# Spike: open the exact Review from a Notification

Research for issue #9. Domain terms (Review, Alert, Notification, Recipient, Tracked Object) follow [the Front Door glossary](../CONTEXT.md).

## Question

Can tapping an iOS Home Assistant Companion App Notification open the exact Frigate Review that caused it, inside the HA app, instead of the latest Review?

## Short answer

Not with the Advanced Camera Card alone, and not soon: the card has no way, in v8.1.0 or current HEAD, to target a specific Review by id or time, and the upstream feature request for it is open and unscheduled. There is no need to invent a "store then read" mechanism, though: the Review's id and time are already known when the blueprint builds the Notification, so the real gap is a card or view that accepts a target id/time in its own config or URL, not a way to get that id into HA. Two workable paths exist without waiting on upstream: (1) HA's built-in media browser can deep-link to one specific event clip today, in-app, with no new dependency, but it opens the generic media browser, not the front-door view, and it targets a Tracked Object's clip, not the Review as a grouping; (2) a per-Notification card built at automation time (via `browser_mod`) that queries Reviews by a narrow time window instead of an id can show the Advanced Camera Card's own Review view scoped to just that Review, at the cost of a third-party dependency and added complexity. A third path, Frigate's own `/review?id=` deep link, is exact and simple but opens outside the HA app when reached through ingress, so it fails the "in the HA app" requirement.

## Findings

### 1. Advanced Camera Card (dermotduffy/advanced-camera-card, v8.1.0)

- URL actions (`?advanced-camera-card-action.<card_id>.<action>`) support the actions `camera_select`, `camera_ui`, `clip`, `clips`, `default`, `diagnostics`, `expand`, `folder`, `folders`, `gallery`, `image`, `live`, `media`, `menu_toggle`, `recording`, `recordings`, `review`, `reviews`, `snapshot`, `snapshots`, `substream_off`, `substream_on`, `timeline`. Of these, only `camera_select` (a camera id) and `substream_on` (a stream name) accept a value from the query string; parsed in `dermotduffy/advanced-camera-card:src/card-controller/query-string-manager.ts:121-176` (tag `v8.1.0`, commit `d2ce00c4d`). Every review/clip/recording/timeline action is built by `createViewAction(actionName, { cardID })` (`src/utils/action.ts:70-81`), which never receives an id or time. The current blueprint's `review` action therefore always opens the latest Review, confirmed by the source, not an assumption.
- The `view` config schema (`src/config/schema/view.ts:134-175`) has no field for a media id or timestamp; `view.default` only selects a named view type.
- The media query types used for `type: reviews`/`recordings`/`events` (`src/camera-manager/types.ts:52-267`, filters in `src/query-source.ts:19-26`) can filter by camera, time range, `limit`, `favorite`, `tags`, `what`, `where`, `reviewed`, `severity` — never by a single id. Confirmed no `id` field exists anywhere in `MediaQuery`/`EventQuery`/`RecordingQuery`/`ReviewQuery`/`QueryFilters`.
- An internal `selectResult.id` / `selectResult.time` capability exists (`src/card-controller/view/types.ts:12-27`, executed in `src/card-controller/view/view-query-executor.ts:216-284`) but is wired only to in-card interactions — timeline clicks, gallery clicks, viewer seeks — never to config, actions, or the URL parser. It is not something an automation can reach.
- `overrides` (`src/config/schema/overrides.ts:1-13`) and `automations` (`src/config/schema/automations.ts:1-43`) can conditionally switch between a fixed, hand-authored set of static config branches based on an HA entity's state matching a literal (`src/config/schema/condition-trigger/conditions/stock/state.ts:12-34`). Neither supports templating a dynamic value (such as an id read from `input_text`) into an action or query field. They cannot express "open the Review whose id is in this helper."
- Maintainer confirmation, unverified via runtime test but explicit in the project's own issue tracker:
  - Issue [#2138](https://github.com/dermotduffy/advanced-camera-card/issues/2138) (closed as duplicate) — the maintainer: "navigation to a specific piece of media is not currently supported. That is requested in [this Feature Request](https://github.com/dermotduffy/advanced-camera-card/issues/1246)."
  - Issue [#1246](https://github.com/dermotduffy/advanced-camera-card/issues/1246) ("Allow querystring navigation to specific event ids") is open and unscheduled as of this research.
  - Issue [#1078](https://github.com/dermotduffy/advanced-camera-card/issues/1078) (closed) — the maintainer, on the query-string mechanism: "It currently can not take you to a specific named event / snapshot (e.g. by an id)."
- **Conclusion**: the card cannot be pointed at a stored Review id or time today, by any public mechanism. This directly confirms the premise in the issue body.

### 2. Frigate HA integration (blakeblackshear/frigate-hass-integration) — media source and proxy

- Frigate exposes browsable media under `media-source://frigate/<frigate_instance_id>/event/<clips|snapshots>/<camera>/<event_id>`, built by `EventIdentifier.__str__` (`blakeblackshear/frigate-hass-integration:custom_components/frigate/media_source.py:189-241`). There is no `ReviewIdentifier` class in this file; media-source browsing is keyed by Frigate **event** id (a Tracked Object) and camera, not by the Review's own id. A Review can contain several events (Tracked Objects), so this URI addresses one Tracked Object's clip, not the Review as a grouping.
- The notification proxy used by the blueprint's `attachment.url` is `NotificationsProxyView`, registered at `url = "/api/frigate/{frigate_instance_id:.+}/notifications/{event_id}/{path:.*}"` with a shorter alias `/api/frigate/notifications/{event_id}/{path:.*}` (`custom_components/frigate/views.py:343-348`). It serves `thumbnail.jpg`, `snapshot.jpg`, `clip.mp4`, `event_preview.gif`, `review_preview.gif`, `review_thumbnail.webp`, and HLS segments (`master.m3u8`/`.ts`/`.m4s`) (`views.py:352-407`), all keyed by the same `event_id` path parameter — again a Tracked Object/event id, not a distinct Review id, though the blueprint's `image_id` (the moving Tracked Object's id) happens to work here.
- Access does not strictly require HA authentication: `_permit_request` (`views.py:409-441`) allows unauthenticated access unless `notification_proxy_enable` is off, gated only by an optional expiry window computed from the event id's embedded timestamp. This is why the blueprint's snapshot attachment already works without a login.
- HA's frontend media-browser panel supports deep-linking to one specific media item via a URL path segment: `/media-browser/<entityId>/<percent-encoded "media_content_type,media_content_id">`, built and parsed in `home-assistant/frontend:src/panels/media-browser/ha-panel-media-browser.ts:44-51,180-224`. This is a real, working in-app route, but it is undocumented as a public deep-link contract (not covered on the home-assistant.io media_source docs page) and requires careful double percent-encoding of the full `media-source://frigate/...` URI as the `media_content_id`.
- **Conclusion**: HA can deep-link, in-app, to one specific Frigate event clip today, with no new dependency, but only at event (Tracked Object) granularity, into the generic media browser UI (no timeline/scrubbing/snooze row), via an undocumented frontend route.

### 3. Frigate UI via ingress

- Frigate 0.18's own frontend does support a review deep link: `<Route path="/review" element={<Events />} />` (`blakeblackshear/frigate:web/src/App.tsx:118`, tag `v0.18.0`), and `Events.tsx` reads the `id` query param, fetches `review/{reviewId}`, and opens the recording at that Review's camera/time (`blakeblackshear/frigate:web/src/pages/Events.tsx:153`, tag `v0.18.0`). A Frigate maintainer confirms this works when linking directly to Frigate's own URL: "if you use the /reviews topic for notifications then just link to `frigate_url/reviews?id=<review_id>` and it will open right to the item" ([blakeblackshear/frigate#6416](https://github.com/blakeblackshear/frigate/issues/6416)).
- There is no `/dashboard` route in Frigate 0.18's own frontend (`App.tsx:110-131`, tag `v0.18.0`); the old automation's URL `/ccab4aaf_frigate/dashboard/review?id={{review_id}}` does not match any current Frigate route and looks outdated or conflated with a different add-on UI. This pattern should not be reused.
- Reaching that same `?id=` deep link through HA's Supervisor ingress (the `ccab4aaf_frigate` add-on slug) is unreliable: ingress URLs are of the form `https://<host>/api/hassio_ingress/<token>/...`, where `<token>` is session-scoped and cannot be pre-generated for a Notification's `url` field (reported in [blakeblackshear/frigate/discussions/19882](https://github.com/blakeblackshear/frigate/discussions/19882); consistent with how HA Supervisor ingress tokens are documented to work). [blakeblackshear/frigate-hass-integration#1078](https://github.com/blakeblackshear/frigate-hass-integration/issues/1078) ("Add deep link support for specific review items via HA companion app") was closed by a maintainer pointing at [blakeblackshear/frigate-hass-addons#87](https://github.com/blakeblackshear/frigate-hass-addons/issues/87) ("Navigate to subpages within HA by url"), which remains open with no confirmed fix.
- Unverified in full primary-source detail: the exact ingress token/slug documentation text on developers.home-assistant.io was not retrieved (page redirected before the relevant section); the slug-format characterization is inferred from the GitHub issues above, not quoted directly from HA's docs.
- **Conclusion**: a Frigate-native `?id=` deep link is exact and simple, but only works reaching Frigate directly, bypassing HA ingress — which means it does not open "in the HA app" as the issue requires. Going through ingress is unreliable and unresolved upstream.

### 4. HA iOS Companion App notification behavior

- Tapping the plain notification body does **not** fire `mobile_app_notification_action`. Source: `PushActionInfo.init?(response:)` returns `nil` when `response.actionIdentifier == UNNotificationDefaultActionIdentifier` (the system identifier for a body tap) (`home-assistant/iOS:Sources/Shared/API/HAAPI.swift`, main branch). Only a defined action button's tap constructs a non-nil `PushActionInfo` and fires the event, via `handlePushAction` called from `home-assistant/iOS:Sources/App/Notifications/NotificationManager.swift`. This corrects a premise in the issue: body-tap-plus-event is not how the current blueprint's `data.url` tap behaves, and never has been — only the explicit Live/Snooze action buttons (which already carry `action_data.tag = review_id`) fire the event. In practice this does not block the goal, because the Review's id and time are already known when the Notification is built, so no event-driven "read it back later" step is needed at all; the target can be baked into the tap URL directly.
- No documented ordering guarantee exists between "open URL" and "event fires" for an action that does both; this is unverified as an official guarantee. Source inspection shows URL navigation is a fast local UI call while the event fire is a network POST, so navigation likely completes first in practice, but this is inferred, not a documented contract.
- iOS notification attachments: documented limits are Image ≤10 MB (JPEG/GIF/PNG), Video ≤50 MB (MPEG/MPEG2/MPEG4/AVI), Audio ≤5 MB (companion.home-assistant.io/docs/notifications/notification-attachments/). A Frigate `clip.mp4` fits the documented video format/size envelope for short clips; Frigate-specific compatibility (codec/container specifics) is unverified — no official doc mentions Frigate. HLS `master.m3u8` is not supported: the attachment model is a single downloaded file, not a streaming manifest, and `.m3u8` is not in the allowed-formats list.
- `browser_mod` (thomasloven/hass-browser_mod, third-party HACS integration) can target a Companion App's own embedded webview, not only separate kiosk "browser" displays: its `browser_id` registration mechanism has no special case excluding the Companion App, and [thomasloven/hass-browser_mod#1364](https://github.com/thomasloven/hass-browser_mod/pull/1364) ("Fix iOS/iPadOS Companion App crash with popup timeout progress") shows the maintainers actively support the Companion App's webview as a target. `browser_mod.navigate` and `browser_mod.popup` accept an arbitrary path or card definition per `browser_id`, both of which HA templates before sending, so a card definition (including Jinja-templated fields) can be built per Notification.
- Current `data.actions` syntax (companion.home-assistant.io/docs/notifications/actionable-notifications/) confirms an action item can carry both `uri` (opens a URL) and its own `action` identifier (fires the event) on the same tap — this already matches the blueprint's Live action, which just doesn't currently carry a Review-specific URL.

## Options compared

| Option | Works in-app | Exact Review | Cost / complexity | Dependencies | Risks |
|---|---|---|---|---|---|
| Status quo: Advanced Camera Card URL action to latest Review | Yes | No — always latest | None | Advanced Camera Card only | Shows the wrong Review if a newer Alert lands before the Recipient taps |
| Wait for upstream Advanced Camera Card fix ([#1246](https://github.com/dermotduffy/advanced-camera-card/issues/1246)) | Yes, once shipped | Yes, once shipped | None now; small config change later | Unscheduled upstream feature | No ETA; may never ship as designed |
| HA media browser deep link to one Tracked Object's event clip (media-source URI) | Yes (in-app frontend route) | Partial — one Tracked Object's clip, not the Review grouping | Moderate — build and double percent-encode a `media-source://frigate/...` URI per Notification; verify it plays, not just browses | `frigate-hass-integration` media_source, HA frontend's undocumented `/media-browser/<entity>/<encoded id>` route | Undocumented route can change without notice; generic media-browser UI, no timeline/scrubbing/Snooze row; targets an event, not the Review |
| Per-Notification card via `browser_mod`, Reviews query scoped by a narrow start/end time window instead of an id | Yes, if the Recipient's Companion App session is registered | Yes, in practice, if no other Review on the same camera overlaps the narrow window | High — add a third-party dependency, register each Recipient's `browser_id`, template a full card config per Alert, add an Open Review action button (a body tap fires no event), handle popup lifecycle alongside existing Snooze buttons | `browser_mod` (third-party HACS), Advanced Camera Card's existing time-range media query fields | Untested; `browser_id` registration is a manual, session-tied step; narrow-window matching is a heuristic, not a guaranteed unique match; adds an external dependency this repo has otherwise avoided |
| Attach the causing clip (`clip.mp4`) to the Notification instead of navigating | N/A — plays inline in the Notification, no in-app navigation | Yes, for the first Tracked Object | Low — swap the attachment URL from `snapshot.jpg` to `clip.mp4` | iOS attachment support (confirmed) | Does not satisfy "open the Review in the HA app" literally; only the first Tracked Object's clip; clips over 50 MB silently fail to attach |
| Frigate's own `/review?id=` deep link, direct (non-ingress) URL | No — opens outside the HA app when reached through ingress | Yes | Low, technically | A directly reachable Frigate URL, bypassing HA | Fails the "in the HA app" requirement; adds an externally exposed surface this project has not otherwise needed (see ADR 0004) |

## Recommendation

Keep the status quo (latest Review) as the safe default; it is a real gap only when a second Alert lands before a Recipient opens the first one, which is the same window the Quiet Window already dampens for sound. Do not build the `browser_mod` + time-scoped card path yet: it is the only option that fully meets the acceptance criteria (in-app, exact Review, keeps the existing card and Snooze row) but it is unverified end-to-end, adds a third-party dependency, and needs a hands-on prototype before committing to it. Track the upstream Advanced Camera Card feature request ([#1246](https://github.com/dermotduffy/advanced-camera-card/issues/1246)); if it ships with an id or time parameter, it replaces this whole workaround with a one-line config change. In the meantime, the HA media-browser deep link is worth a small, low-risk follow-up test since it needs no new dependency, even though it only reaches event granularity and a generic UI.

## Draft follow-up ticket

**Title**: Prototype a per-Notification, time-scoped Advanced Camera Card popup via browser_mod

**What to build**: A spike. Add an **Open Review** action button to the Alert Notification, carrying the Review's camera and `start_time` in `action_data`. A body tap can't be used, because it fires no `mobile_app_notification_action` event (Findings §4). When the button is tapped, the automation calls `browser_mod.popup` on that Recipient's registered `browser_id`. The popup holds an Advanced Camera Card for the Review's camera, with a `media: {type: reviews}` query limited to a narrow `start`/`end` window around the Review's `start_time`. There is no Review id field to filter on (Findings §1). Compare the result with opening the front-door view's existing card.

**Acceptance criteria**:
- [ ] Tapping **Open Review** opens a popup showing only the Review that caused it, even with the app closed or in the background, on a real device, for at least 10 real Alerts including two Alerts on the same camera within a few minutes of each other.
- [ ] The popup or view keeps (or has a documented reason not to keep) the existing Snooze row and scrubbing profile.
- [ ] `browser_id` registration for each Recipient's Companion App is documented as a one-time setup step, and its behavior after the Companion App is force-quit and reopened is verified.
- [ ] A written comparison against the HA media-browser deep link option, on real hardware, with a recommendation to adopt one, keep both, or drop the spike.

**Blocked by**: #9 (this spike)

## Open questions

- Does a narrow `start`/`end` window ever match more than one Review on the same camera in real traffic, given the padding Frigate applies (`REVIEW_PADDING` in `blakeblackshear/frigate:web/src/pages/Events.tsx`)? Unverified without production traffic data.
- Does `browser_mod`'s `browser_id` survive the Companion App being force-quit and relaunched, or only being backgrounded? Unverified from docs; the FAQ entry on session-based Browser ID synchronization suggests staying logged in is what matters, but this needs a device test.
- Does the HA media-browser route (`/media-browser/<entity>/<encoded id>`) actually start playback on load, or only browse to that item's listing? Unverified; the source confirms routing and parsing, not the resulting UI state.
- Would opening `media-source://frigate/.../event/clips/<camera>/<event_id>` for one of a Review's several Tracked Objects (rather than the first-reported one used for the snapshot today) more usefully represent "the Review" to a Recipient? Open design question, not a technical one.
